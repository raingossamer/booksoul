# BookSoul Web — Spec

> 上游：`Todo/Grills/booksoul-web-grill.md`（D1–D9 已由用户逐条确认，本 Spec 直接采信，不再重复论证）
> 范围约束：**先在本地跑通**（用户决定，见 Grill D7），部署与多实例不在本轮。

## Problem Statement

booksoul 现在是一个命令行工具。它能把 epub / mobi / azw3 / pdf / docx / txt / html / md 解析成模型读得懂的 Markdown，
能以三种人格（研读者 / 作者本人 / 书本身）基于书的原文与读者对话——但这一切只有会开终端、会配环境变量、
会 `pip install` 的人才用得上。

想读书的人用不了它。而这个工具真正的价值恰恰是给读者的：把一本书交给模型之前先让它变成模型读得懂的样子，
然后让书回答你自己的困惑。

具体的阻碍有四层：

1. **进不去**：没有界面。上传一本书要敲 `booksoul parse 某本书.epub`。
2. **不是自己的**：书库是本机一个目录，没有账号概念，几个人用同一台机器就是同一个书库。
3. **看不见过程**：解析成功还是失败、中间清洗动了哪些地方、回答到底读了书里哪几节，全在终端一闪而过。
4. **信不过**：模型答完了，读者无从判断它是真读了原文还是在凭训练时的印象复述。

## Solution

把解析引擎保持原样，在它外面长出一层多用户 Web 产品：**上传 → 解析入库 → 个人书库 → 阅读溯源 → 选书选人格对话**。

四个关键取向，每一个都是为了让「信得过」落地：

- **解析过程摊开给人看**。五个阶段实时推进度；成功后给一份可逐条核对的账（合并了多少硬换行、
  剥了多少全角空格、脚注接上几条）；失败明确说停在哪一步、给出用户自己能执行的补救。
  抽不出文字的扫描版 PDF 宁可停下，也不写出一个空 md 假装成功。
- **回答的依据可查**。每次回答都能翻出「这次读了全书 16 节里的哪 5 节」，附 BM25 排名、命中词、
  预算线，以及「下一节差 504 字装不下」这种具体到字数的解释。
- **引文能跳回原文**。回答里的每处引用都带锚点，点一下落到那一章那一段并高亮，还留着回对话的路。
- **密钥不归服务器**。用户自带模型 API key，只存在他自己的浏览器里；服务器每次转发、从不保存。

## User Stories

**账号与书库归属**

1. 作为一个新用户，我想用邮箱注册并登录，以便拥有一个只属于我的书库。
2. 作为一个已登录用户，我想在刷新页面后仍保持登录，以便不必反复输密码。
3. 作为一个用户，我想确信别人看不到我的书和我的对话，以便放心上传私人藏书。
4. 作为一个首次登录的用户，我想看到一个说明这个产品做什么的空书库页，以便知道第一步该做什么。

**上传与解析**

5. 作为一个读者，我想把书拖进浏览器就开始解析，以便不必接触命令行。
6. 作为一个读者，我想一次拖入多个文件，以便一口气把藏书导进来。
7. 作为一个读者，我想让系统按文件内容而不是扩展名判断格式，以便下载来的书扩展名标错了也能正常解析。
8. 作为一个读者，我想实时看到解析进行到哪一步（读取 / 解析目录 / 转换正文 / 清洗 / 写入），以便知道它没卡死。
9. 作为一个读者，我想在解析大部头时看到具体进度（如「转换正文 41/64 节」），以便估计还要等多久。
10. 作为一个读者，我想在上传前就知道这个站点支持哪些格式，以便不上传注定失败的文件。
11. 作为一个读者，当我上传的是扫描版 PDF 时，我想被明确告知它没有文字层、需要先做 OCR，并拿到一条可以直接复制执行的命令，以便自己解决而不是干等。
12. 作为一个读者，当某个文件解析失败时，我想其余文件不受影响照常入库，以便一次失败不毁掉整批导入。
13. 作为一个读者，我想在服务重启导致解析中断后看到这本书被标为失败并能重新解析，以便它不会永远卡在「解析中」。

**质检与核对**

14. 作为一个读者，我想看到一份解析报告，列出系统改动了正文的哪些地方，以便判断它有没有改坏。
15. 作为一个读者，我想在目录树上看到每章字数条，以便一眼发现异常短的章节。
16. 作为一个读者，当某一章只有几个字时，我想被提示去核对，以便确认它是分部标题页还是丢了正文。
17. 作为一个读者，我想把核对过的存疑项标记为已处理，以便下次不再被同一条打扰。
18. 作为一个读者，我想知道元信息里哪些字段是原文标注的、哪些是系统猜的，以便不被「译者」这类猜测误导。
19. 作为一个读者，我想在解析质量不满意时重新解析这本书，以便修正章节切分或编码问题。
20. 作为一个读者，当我要重新解析一本书时，我想被告知有几个进行中的会话会受影响，以便决定要不要现在做。

**阅读与溯源**

21. 作为一个读者，我想在网页上直接阅读解析好的正文，以便不必另外找阅读器。
22. 作为一个读者，我想通过目录树跳到任意一章，以便快速定位。
23. 作为一个读者，我想看到脚注的内容而不必跳到页尾，以便阅读不被打断。
24. 作为一个读者，我想知道当前这一章在全书中的位置，以便建立整体感。
25. 作为一个读者，我想看到这一章对应的 Markdown 源文件路径，以便自己拿走或手工修订。
26. 作为一个读者，当我从对话里点击一处引文时，我想直接落到那一章那一段并看到它被高亮，以便核对模型有没有引对。
27. 作为一个读者，从引文跳到原文后，我想看到是哪个问题把我带过来的，并能一键回到那段对话，以便不迷路。
28. 作为一个读者，当引文因为重新解析而定位不到时，我想看到明确的「原位置已变更」而不是一个点了没反应的按钮。

**对话**

29. 作为一个读者，我想选一本书开始对话，以便让模型基于这本书的原文回答我。
30. 作为一个读者，我想在研读者 / 作者本人 / 书本身三种人格间切换，以便得到三种性质不同的回应。
31. 作为一个读者，我想用「对读」把同一个问题的三种人格回答并排看，以便直观感受它们的差别。
32. 作为一个读者，看完对读后我想挑其中一种人格接着聊下去，以便把那条线索深入下去。
33. 作为一个读者，我想让回答逐字流式出现，以便不必盯着空白等待。
34. 作为一个读者，我想打开「处境模式」，把我自己的困惑而不是关于书的知识问题抛给它，以便让书照见我的处境。
35. 作为一个读者，我想让模型在书照不到我的处境时直说照不到，以便不被一段贴给谁都成立的道理糊弄。
36. 作为一个读者，我想保留对话历史并在书库首页看到最近问过什么，以便随时接着上次聊。
37. 作为一个读者，当网络断开或服务重启导致回答生成到一半中断时，我想已经生成的部分被保住，以便不白花自己的额度。
38. 作为一个读者，对于中断的回答我想能选择重问或让它接着往下说，以便自己决定要不要再花一次钱。
39. 作为一个读者，我想确信重连不会让同一个问题被重新提交给模型，以便不为一次提问付两次钱。

**检索与预算**

40. 作为一个读者，我想知道这次回答读了全书的哪几节，以便判断它的依据够不够。
41. 作为一个读者，我想看到每一节的 BM25 相关度、命中词和字数，以便理解为什么是这几节被选中。
42. 作为一个读者，我想看到预算线画在哪里、下一节差多少字装不下，以便明白取舍发生在何处。
43. 作为一个读者，当我的新问题涉及一节没被载入的内容时，我想被提示，并能选择重新选章，以便不在模型没读过的部分上得到臆测。
44. 作为一个读者，我想被告知重新选章会重置缓存（意味着这一轮更贵），以便自己权衡。
45. 作为一个读者，当整本书装得下时，我想知道模型拿到的是全书而不是片段，以便对回答更有信心。
46. 作为一个读者，我想看到这次调用花了多少输入 / 输出 token、命中了多少缓存，以便对成本有感。

**大脑与密钥**

47. 作为一个读者，我想在多个模型后端之间选择（Claude / 通义 / DeepSeek / Kimi / 智谱 / 硅基流动 / OpenAI / 本机 Ollama），以便用自己有额度的那个。
48. 作为一个读者，我想填入自己的 API key 并保存在本机，以便不必每次重填。
49. 作为一个读者，我想确信服务器不保存我的 key，并看到一句说清楚它如何被使用的话，以便判断自己在信任谁。
50. 作为一个读者，我想在填 key 的输入框里看到掩码而不是明文，以便旁边有人时也能安全操作。
51. 作为一个读者，我想知道当前这本书装不装得进我选的模型，以便提前预料要不要挑章节。
52. 作为一个读者，当某个后端因为内容审核拒绝了请求时，我想拿到可操作的建议（换个大脑或调小预算），以便绕开而不是卡住。
53. 作为一个读者，我想添加任意 OpenAI 兼容的自定义端点，以便接入公司内网或本地模型。
54. 作为一个读者，我想查看并修改三种人格的提示词，以便按自己的口味调校对话风格。

## Implementation Decisions

### 采信 Grill 报告（D1–D9，不再重复论证）

D1 选章锚定会话 / D2 对读分支模型 / D3 目录名带 book_id 且引擎增开按路径入口 /
D4 按 word_count 分流且按需读章节 / D5 密钥措辞改为事实且堵 `__repr__` /
D6 格式支持由运行时探测驱动 / D7 范围收窄至本地单实例 / D8 断流保住已生成内容 /
D9 重解析清空选章并重定位引文。细节见 Grill 报告第 1 节。

### 新增决策（本次访谈确定，未经拷问）

- **N1 · 异常消息规范按层区分**（裁决 Grill R1）。面向用户的边界（HTTP 层、`library`、`config`、
  `persona`、以及用户可执行补救的解析失败）**必须**给出可选值或下一步动作；引擎内部路径
  （`epub.py` / `docx.py` / `plain.py` 的「没有解析出任何正文」等 17 处）允许只陈述事实，
  由调用方翻译成用户语言。理由：实测 48% 的分布本就沿这条线分裂，强行统一会让引擎内部堆砌
  它无从知晓的上下文（引擎不知道调用者是 CLI 还是 HTTP）。写入 `backend.md` 规范章节。
- **N2 · 上传体积上限 100 MB**，前后端共用同一常量，由 `GET /api/formats` 一并下发。
- **N3 · azw3 标为实验性**（裁决 Grill R4）。`mobi` 包解析 azw3 会落临时文件且不支持新版 KFX，
  在格式列表中单独标注，失败时的提示语区别于其它格式。
- **N4 · 认证参数**：access_token 30 分钟、refresh_token 14 天、bcrypt cost 12、密码最短 8 位。
  本地阶段不做邮箱验证、不做找回密码。
- **N5 · 人格提示词维持全局**（裁决 Grill R3）。本轮不建 `user_personas` 表，
  `PUT /api/personas/{key}` 直接改项目根 `prompts/` 下的文件，改动对所有用户生效。
  本地单人使用场景下这是正确的简化；多用户上线前必须回头处理。

### 模块

**引擎（`src/booksoul/`）—— 三处小改，签名向后兼容**

| 模块 | 改动 | 对应 |
|------|------|------|
| `config.py` | `api_key` 字段加 `repr=False` | D5 |
| `writer.py` | `write_book(book, out_root, *, dir_name: str = "")` | D3 |
| `library.py` | 拆出 `load_from_path(path, *, only_idx: set[int] | None = None)`，`load()` 改为调用它 | D3 D4 |

**新增 HTTP 层（`src/booksoul_api/`）—— 分层 `routers → services → repositories → models`**

`services` 是唯一允许 import 引擎的层。

**三个深模块**（封装复杂度、接口简单稳定、脱离 DB 与 HTTP 即可测试）：

- **ChapterSelector** —— 选章的全部决策。输入书的章节、问题、预算、已锁定的章节集合；
  输出选中的章节集合与一个说明性的理由对象（整本装下 / BM25 选出 / 复用会话锁定 /
  新问题命中未载入章节需重选）。会话锁定、逃生门判定、`word_count` 分流判据全在这里。
  不碰数据库、不碰模型 API。
- **CitationRelocator** —— 引文重定位。输入一批引文文本与一组新章节；输出每条引文的
  (章节, 段落序号) 或未命中。纯字符串处理，无副作用。
- **StreamRecorder** —— 流式落库与断流保护。以上下文管理器形式提供一个文本累积器，
  正常退出时一次性持久化完整消息，异常退出时持久化残缺消息并置 `complete = false`。
  把「正常路径零额外开销、异常路径不丢内容」这条约束收进一个地方。

**其余服务**（编排为主，不算深模块）：`ParseService`（上传→解析→写盘→落索引→心跳）、
`LibraryService`、`ChatService`、`BrainService`、`FormatCapability`（启动时探测可用格式）。

### Schema 变更

在 `Design/database/sql.md` 既有 11 张表基础上：

| 表 | 变更 |
|----|------|
| `conversations` | 增 `selected_chapter_ids JSONB` |
| `messages` | 增 `turn INTEGER`、`persona persona_key NULL`、`complete BOOLEAN NOT NULL DEFAULT true`；唯一约束改为 `UNIQUE NULLS NOT DISTINCT (conversation_id, turn, persona)` |
| `retrievals` | 外键从 `message_id` 改为 `conversation_id` + `turn`，唯一约束 `(conversation_id, turn)` |
| `books` | `storage_path` 加 `UNIQUE` |
| `parse_jobs` | 增 `heartbeat_at TIMESTAMPTZ` |

迁移：Alembic `0001_init` 直接生成变更后的最终形态（尚无历史数据）。

### API 契约

相对 `Design/backend.md` 的增改：

- 新增 `GET /api/formats` —— 实际可用格式、体积上限、实验性标注
- `GET /api/messages/{messageId}/retrieval` 改为 `GET /api/conversations/{id}/retrieval`
- `POST /api/conversations/{id}/ask` 请求体增 `compare: boolean`（对读），响应 SSE 的
  `token` 事件增 `persona` 字段以区分三路
- `POST /api/books/{bookId}/reparse` 响应体增受影响会话数
- SSE 事件统一为 `stage` / `token` / `done` / `error`；解析与对话共用同一套约定

## Testing Decisions

**什么算好测试**：只测外部可观察的行为，不测实现细节。断言落在「给定这样的输入，产出这样的结果」上，
不断言内部调用了哪个函数、用了什么数据结构。测试名说明的是被保护的行为，不是被调用的方法。

**已有测试的写法即先例**：`tests/test_parsing.py` 现有 40 条，每一条对应一个真实踩过的坑，
函数名是中文的一句陈述（`test_章节标题与正文句子不混淆`、`test_正文开头与章节标题重复的标题被去掉`），
docstring 写清楚这个坑是什么。新测试沿用这个写法——**一条测试保护一个具体的失败**。

**要测的模块**

| 模块 | 测什么 |
|------|--------|
| `ChapterSelector`（深） | 整本装得下时不跑 BM25 全量返回；装不下时按预算截断且返回原书顺序；会话已锁定时原样复用不重选；新问题命中未载入章节标题时给出需重选的信号；预算连一章都装不下时至少给最相关的一章 |
| `CitationRelocator`（深） | 正文未变时全部命中；章节切分变化后仍能跨章命中；正文被改写后未命中且不误报；引文含全角空格 / 脚注标记时的归一化 |
| `StreamRecorder`（深） | 正常结束落一条 `complete = true`；中途抛异常落一条 `complete = false` 且保住已累积文本；零 token 时不落空消息 |
| `writer.write_book` | 给了 `dir_name` 用它；不给保持原行为；同名书在不同 `dir_name` 下互不覆盖 |
| `library.load_from_path` | 按路径直取等价于原 `load()` 的结果；`only_idx` 只读指定章节；文件缺失时 `warn` 后继续而非抛错 |
| `config.BrainConfig` | `repr()` 不包含 api_key |

**不测**：FastAPI 路由的参数绑定与序列化（框架职责）、SQLAlchemy 的 CRUD（ORM 职责）、
真实模型 API 调用（花钱且不稳定，用假的 brain 替身）。

**不做 API 端点集成测试**（本轮）。理由：本地跑通阶段，端到端的信心由手工走查四条链路获得，
自动化集成测试的维护成本此时高于收益。三个深模块脱离 DB 与 HTTP 即可测试，这是它们被这样切分的原因。

## Out of Scope

- **部署**：多实例、Redis / arq 任务队列、SSE 跨实例 pub/sub、容器化、CI（Grill D7 用户决定）
- **移动端与响应式**：九屏界面稿均为 1280×860 桌面尺寸，断点未设计
- **登录 / 注册页的视觉设计**：界面稿未覆盖，本轮按既有 design token 直接实现
- **邮箱验证、找回密码、第三方登录**
- **书籍版本化**：重解析不保留历史版本（Grill D9 已否决 `book_versions`）
- **服务端统一密钥与配额计费**：key 由用户自带，成本落在用户身上，本轮无配额需求
- **人格提示词的多用户隔离**：见 N5，本轮维持全局文件
- **向量检索 / 语义召回**：`retrieve.py` 模块 docstring 已说明，召回不足的正解是调大预算让整本进上下文，
  而不是堆检索策略
- **书籍去重的强制拦截**：只提醒不阻止（Grill D3）
- **格式化与静态检查工具的引入**（Grill R2 仍未裁决）

- **Grill R5 需实测**：断流后「接着往下」的续写效果不稳（把残文塞回 assistant 角色让模型续写，
  多数模型支持但质量不保证）。先实现，效果不佳则退化为只留「重问」。
- **缓存是这个产品的成本结构核心**。`brain.py:build_system()` 把缓存断点放在全书之后、人格之前，
  这一个设计决定同时支撑了三件事：多轮对话不重复计费、切换人格不失效、对读三次调用共享同一份书的缓存。
  实现时任何改动系统提示拼装顺序的行为都要意识到它会直接体现在用户的账单上。
- **本地开发的两个高频触发点**：`uvicorn --reload` 存文件即重启，会同时触发孤儿解析任务（D7）
  和断流（D8）。这两条不是为生产环境设计的，是本地每天都会踩的。
