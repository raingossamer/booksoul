# Brain Model Picker — Grill Report

> 需求原话：「填入 key 之后能根据填入的 key 做下拉列表去选模型，选择模型去当大脑。」
> 背景：内置预设的模型写死在引擎 `booksoul/config.py:PRESETS`（qwen → `qwen-plus` 等），
> 网页上改不了；今天唯一的出口是「添加自定义端点」手填 base_url 与模型名。

## 1. 确认的决策

| # | 决策 | 来源 |
|---|------|------|
| D1 | **下拉 + 手填并存，永不关掉手填。** 点「列出模型」能列出来就进下拉，附「共 N 个，来自 {base_url}」；列不出来就地退回输入框，并说清是哪一类失败 ——「这个端点没提供模型列表」「key 没通过验证」「超时」三者用户的下一步不同，不能压成一句。列出很多时按名字含 chat / instruct / turbo 的排前，保留搜索框，不做别的过滤 | Q1 |
| D2 | **选择只影响以后新开的会话；已有会话锁定开会话那一刻的模型。** 并修掉现存的分叉：`ask()` 真正调模型时用 `conversation.model` 覆盖配置里的那个，让「显示的、算预算的、实际调用的」三者永远是同一个 | Q2 |
| D3 | **新建一张小表存「我给某个内置预设选了哪个模型」**：`(user_id, brain_name, model, context_tokens)`。解析 = **预设**（`provider` / `base_url` / `api_key_env` 永远从代码来）**+ 选择**（只覆盖 `model` 与窗口）。恢复默认 = 删掉那一行。预设与自定义端点仍是两种东西，`add_custom()` 拒绝与预设重名的禁令**不动**。自定义端点不进这张表 —— 它的 `brains.model` 本来就有，下拉只是帮它填对 | Q3 |
| D4 | **窗口三级取值，来源写在界面上：** ① 供应商在模型列表里报了 → 用它，标「来自供应商」；② `_CONTEXT_BUDGETS` 子串命中（不是落到 `default`）→ 用它，标「内置」；③ 都不知道 → **不默默猜**，输入框预填保守估计（100k）并标「估计值 —— 建议填上真实窗口」，⑧屏那一格显示「窗口未知（按估计）」。**窗口只解析一次，随模型一起快照进 `conversations`**（新列 `context_tokens`）；提问时的预算读快照；**快照为 0 = 历史会话，走今天的老路径，不回填** | Q4 |
| D5 | **后端代理** `GET /api/brains/{name}/models`，key 经 `X-Brain-Key`，与提问同一个信任模型。四条边界：① 列模型的逻辑放进引擎 `booksoul/brain.py`，与 `create` / `chat` 挨着，各家格式差异只存在一处；② **只回模型 id（和供应商报了的窗口），绝不回原始响应体** —— 堵住「按用户填的 base_url 把内网响应回显出来」的口子；③ 失败复用 `BrainError.kind` 分类；④ `client.ts` 注入 `X-Brain-Key` 的白名单从「仅对话端点」扩到这一个；超时约 10 秒 | Q5 |
| D6 | **第一版只给已存在的大脑下拉**：9 个内置预设 + 已保存的自定义端点。「新建自定义端点」表单仍手填模型名，存下来之后那一行就能「列出模型」改。省掉的是一个「拿着任意 base_url 去探」的端点 —— 这个功能里唯一一处新增的攻击面 | Q6 |
| D7 | 细节默认值（常规答案，未单独拷问）：只在点「列出模型」时拉；**服务端不缓存**（列表取决于 key，而 key 用完即丢），前端存在组件状态里；手填的名字不在已拉到的列表里 → 提示但不拦，不为校验单独再打一次供应商；ollama / lmstudio 是本机端点，列表请求不带 `X-Brain-Key` | 拷问收尾 |

## 2. 发现的冲突

| # | 冲突 | 处置 |
|---|------|------|
| C1 | **`brains` 表的文档与代码不一致。** `database-relations.md:18,34` 与 `data-er.md:177` 说 `user_id IS NULL` 的行是内置全局预设；实测表里 **0 行**，内置预设来自引擎 `available_brains()`（`brain_service.presets()`） | 代码的做法是对的（CLI 与网页共用一份预设，符合「同一条规则只许有一份实现」），**文档过期**。本功能收尾的 design-doc-sync 修正文档 |
| C2 | **同一个会话的模型有两份真相。** 真正调模型读 `config_for()` 现查的当下配置（`chat_service.py:307,374`）；显示与预算读 `conversations.model` 快照（`:247,323,553`）。今天预设写死所以两份永远一样；选模型一上线，旧会话下一轮会**调新模型、却显示并按旧模型算预算** | D2 修 |
| C3 | **自定义端点的窗口分叉（已在生产、尚未被踩到）。** ⑧屏「装得下吗」用 `brains.context_tokens`（`brain_service.py:306`）；提问时 `context_budget_chars(conversation.model, ...)` **只查内置表**，认不出的名字按 `default: 100_000`。正是 `ask.py` 注释那句警告的原样复现：「设置页说『装得下』而提问时却在挑章节」。《悉达多》4.8 万字两边都装得下，所以没显形 | D4 修（同一个根因） |
| C4 | `frontend.md`「API 调用层」写 `client.ts` 注入 `X-Brain-Key`「**仅对话端点**」 | D5 扩白名单，同步更新该节 |
| C5 | `data-er.md` 承诺「日后改了预设也不会篡改历史记录的真实来源」—— 对**已落库的消息**成立，对**旧会话的下一轮**不成立（C2） | D2 修之后承诺完整成立 |

## 4. 风险清单

| # | 风险 | 缓解 |
|---|------|------|
| R1 | **各家 `/v1/models` 的真实行为未经实测**：DashScope 兼容模式、智谱是否提供；返回的是否是 key 真有权限的那批；是否带窗口字段 | 测试用替身（与 `conftest.fake_brain` 同一思路，换在引擎那一层）；实施时用真 key 逐家点一遍，结果记进计划完成记录。D1 的手填兜底保证「列不出来」不会让任何一家变得比今天更难用 |
| R2 | 服务端按用户填的 `base_url` 发请求（自定义端点）= SSRF 面 | 提问那条路已存在同样的面；列模型这条靠 D5②「只回 id 不回原文」限住回显；D6 不开任意地址探测；compose 端口绑 127.0.0.1 |
| R3 | 估计值仍可能错 | 用户不改估计 → 行为与今天相同；区别是界面**明说**那是估计，不再冒充事实 |
| R4 | 新表按**名字**弱关联内置预设，预设改名或删掉 → 选择行成孤儿 | 解析时找不到对应预设就忽略该行，列表里不显示；不报错、不崩 |
| R5 | 平台级内容审核（通义拦《悉达多》）**与本功能无关**，换模型解决不了 | 已向用户说明；不在本功能范围 |
| R6 | `conversations` 加 `NOT NULL DEFAULT 0` 列 | PostgreSQL 11+ 带常量默认值加列是元数据操作，不重写表 |

## 5. 下一步建议

标准路径：`write-a-spec`（自动衔接）→ 人工 review Spec → `spec-to-plan` → `tdd` → `design-doc-sync`。

建议的切片顺序（由 spec-to-plan 最终裁定）：

1. **引擎 `list_models`**：纯能力 + 替身测试；Anthropic 与 OpenAI 兼容两种形状、失败分类 —— 零依赖，可最先做
2. **迁移 `0003`**：新表 + `conversations.context_tokens`；漂移检测覆盖
3. **会话快照**：开会话快照模型与窗口、提问读快照 —— 修 C2、C3；**不依赖新表即可独立验证**，建议早做，因为它修的是已存在的缺陷
4. **解析合并**：`config_for` / `list_for_user` 读选择；三级窗口取值
5. **端点**：列模型 / 存选择 / 恢复默认
6. **前端**：⑧屏下拉 + 手填 + 窗口来源标注；`client.ts` 白名单
